# 0002. リプライを独立したアプリにしない

**ステータス**: 採用（2026-07-29）

## 背景

サイドバーでは「ツイート」と「リプライ」が別項目として並び、画面も分かれている。
一方でリプライは tweets テーブルに保存されるため、独自のモデルを持たない。
この状態で replies アプリを新設すべきか判断が必要になった。

## 決定

replies アプリは作らない。リプライの確認・返信は tweets アプリの中に
ビューと URL を追加して実装する。

## 理由

- リプライは Tweet モデルそのもの。replies アプリを作っても models.py は空で、
  tweets.models.Tweet を import するだけになる
- X API 側もエンドポイントが同一。投稿は `POST /2/tweets` に
  `reply.in_reply_to_tweet_id` を添えるだけで、取得しても返るのは同じ tweet
  オブジェクト。API を叩く処理とレスポンスを DB に落とす処理が投稿と完全に
  共通するため、アプリを分けると共通コードの置き場所とアプリ間 import の
  問題だけが増える
- アプリ分割の基準は「他のアプリに寄りかからずに成立するか」に置く。
  dm は独自モデルと別系統の API を持つため成立する。api_usage はモデルを
  持たないが、localStorage 上の料金計算だけで完結するため成立する。
  replies は tweets が無いと何もできない
- 画面の境界とアプリの境界は一致しなくてよい。tweets アプリ内に別のビューと
  URL パターンを置けば `/replies/` という URL は作れる
- api_usageも独立したmodelを使用しないアプリだが、api_usageは他ページと機能があまりにも違
  うため独立したアプリにしている。
  リプライページはおそらく、ツイートページとほとんど同じ機能になるため独立したアプリにするべきではない。
